# Tokyo Night and Terminal Color Hints

> Historical 1.1.0 implementation record. Remote `ls/ll` injection has since been removed; see the [current terminal color guide](../TERMINAL_COLOR_SCHEMES.md).

## Appearance and Settings

Only the terminal surface and preview use Tokyo Night: the light Day background and the text inside the cursor are adjusted to pure white `#FFFFFF`, while the dark Night theme is unchanged; the title bar, SFTP and session cards are unchanged. The fixed color values, source commits and license live in `Vendor/TokyoNight`, and the upstream original files are left untouched. The original ANSI 16 colors are not changed; local semantic accent colors are adjusted against the background to at least 4.5:1 to guarantee readability on Day.

On the first upgrade, `com.snake.terminal.tokyo-migration-v1` selects Tokyo Night once, after which the user's choice is restored; Classic and Vivid remain selectable. New `com.snake.terminal.field-highlight` and `com.snake.terminal.shell-colors` toggles are added, both on by default. The log toggle is kept separate.

The theme, font, log and field highlighting are applied immediately to the original terminal view without rebuilding the SSH connection; the colored ls/ll toggle takes a snapshot when the connection starts and takes effect on the next connection, and does not inject commands into a Vim/top that is in use.

## Two Layers of Color

1. Remote file types: the Shell initialization detects GNU/BSD ls and configures ANSI base color rules. Directories blue, symbolic links cyan, executables and source code green, archives purple, configuration files orange-yellow. Regular files keep the default color. BSD supports only its native file-type classification and does not provide GNU extension rules.
2. Local fields: permissions cyan, date/time blue-gray, addresses blue, paths cyan, sizes/percentages orange, success/running green, failure red, stopped/warning orange. The original log-level rules are preserved, and bare numbers or relative paths are not highlighted by default.

Local rules only modify display attributes and do not change the terminal buffer, copied text or remote bytes. ANSI/True Color, selection, reverse video and hidden attributes take precedence; the alternate screen is disabled. Command echo on the normal screen may match, and full Shell input syntax analysis is not performed.

Matching order: errors and warnings, paths/addresses/date-time, permissions/sizes/status, and finally ordinary log levels; ranges are not covered twice. Semantic highlighting and the original log toggle are controlled separately. IPs are validated through system address resolution.

## Shell Initialization Boundaries

- Supports bash, zsh and fish, following the existing OSC 7 initialization order, once per connection. There is no remote file writing, software installation, permanent alias or configuration modification, and it does not rely on SSH AcceptEnv.
- Uses newline-separated function definitions to avoid exceeding the remote TTY's single-line length limit; the function is called only after it is fully defined, and then the helper function is cleaned up.
- GNU is detected through `--version` and colored-option capability and uses `--color=auto`; BSD uses `-G` and CLICOLOR. FORCE_COLOR is not set and colors are not forced on pipes.
- Existing LS_COLORS entries are preserved as-is and only missing keys are filled in; existing LSCOLORS is preserved. When NO_COLOR is non-empty all color settings are skipped, and unrelated variables such as SYSTEMD_PAGERSECURE are not adjusted.
- When ll is missing, a long-list alias is created. An existing simple alias that directly calls ls is allowed only for textual options, keeping its arguments and adding color; repeated initialization does not add the trailing color option again.
- Complex functions, complex aliases, explicit color disabling and an existing independent ll command are preserved, with a brief non-blocking explanation. For fish, only functions that can be confirmed to be generated by an alias and whose body is direct ls arguments plus argv are handled; functions are not rewritten arbitrarily.
- Unsupported Shells/ls and initialization failures do not change the connection state or trigger a reconnect. It is not guaranteed that a user's complex ll function automatically gains color; this is a deliberate boundary that preserves server-customized behavior.
- The initialization definition may appear in the remote interactive Shell's echo/command history and contains no credentials; "does not write configuration files" is not the same as disabling the Shell's own history mechanism.

## Verification

```sh
swift test --disable-sandbox
GITHUB_ACTIONS=true swift test --disable-sandbox --package-path Vendor/SwiftTerm
docker build -f scripts/terminal-color-test.Dockerfile -t snake-terminal-color-test:local scripts
SNAKE_SHELL_COLOR_DOCKER_IMAGE=snake-terminal-color-test:local swift test --disable-sandbox --filter TerminalShellColorTests
```

The Shell tests run through a pseudo-terminal and use a temporary HOME and directory/link/executable fixtures to check aliases, NO_COLOR, user colors and pipe output. Local coverage uses BSD ls, while Docker covers GNU ls in a temporary container with read-only mounts and no network; it does not start an SSH service or access user servers or real credentials. These tests verify the behavior of the initialization script in a real Shell and are not equivalent to real SSH GUI acceptance.

The app tests cover upstream color-value consistency, one-time migration, positive and negative semantic-matching cases, independent toggles, Unicode, long-path soft wrapping, buffer invariance and over-limit skipping; they reuse the view-identity, selection, ANSI/True Color, alternate-screen and performance tests.

The pre-existing `invalidMapping` failure of `MountOperationsTests.testQuitIsCancelledWhenMountIsBusyOrMountTableCannotBeRead` is still recorded separately, and the mount logic is not modified. The pages are accepted by the user: ls/ll after a new connection, light/dark themes, long logs, Vim/top, selection copy and multiple splits.

- Final full app test run: 114 tests, 111 passed, 2 pre-existing integration tests skipped by condition, and the 1 mount test above failed. The 7 Shell-specific tests passed on both the local BSD and the Docker GNU environment; all 16 theme-and-output tests passed.
